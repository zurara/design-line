# design-line

A production line for design work run through Claude Code. One pipeline shape, instantiated once per kind of thing you make. Your organization, your preferences and your design rules live in a profile folder, not in the plugin, so the same plugin runs for any studio and any designer.

## The shape

```
read ──▶ brief ──▶ [you approve] ──▶ write ──▶ check ──▶ ship ──▶ record
```

A **lane** is one kind of work: a component library, prototypes, a design-tool file, illustrations, documents. Every lane has the same six stations. A **task** walks them in one session; the session is that task's coordinator and ends with the task. What the next session needs is in files.

## The roles

| Role | May | May not |
| --- | --- | --- |
| `line-coordinator` (the session) | read everything, write the brief, dispatch, ship as the lane allows, record | push / PR / publish without your yes where the lane says so |
| `line-reader` | read code, design files, planning pages; return bounded tables | edit, install, build, commit, write anywhere |
| `line-writer` | write in one worktree from an approved brief, commit | push, merge, publish, ask you, touch shared files |
| `line-checker` | run the gate, measure light and dark, screenshot | fix anything |
| `line-ledger` (optional) | reconcile what shipped with your planning tool, draft proposals | write there without your yes |

## The inbox

Things come up mid-task. They go into `_line/inbox.md` the moment you say them, one line each, and the task continues. Four cases: blocks the task (becomes a sub-brief now); belongs to another lane (parked for that lane); small (done now, one commit, one ledger line); run in parallel (another writer, another worktree). When a task ends you are asked one thing: which item next, or stop.

## Fits the plan you pay for

`init` asks which plan you are on and sets `budget:` in lanes.yaml: on Pro the board pushes are off, tasks run one at a time on small models, and the dispatcher is not recommended; on Max the batches and the live board come on. Nothing in the budget removes a check, your yes, or the ledger.

## Walking away

`/design-line:run` loads a batch while you are here (briefs, every decision answered one at a time, whether to ship), then runs each approved task as its own subagent while you are gone, parks anything it cannot answer, and gives you one report when you return. One light resident instead of three heavy ones.

## Seeing it from a phone

Publish `templates/board.html` once as an artifact with the `db` capability and put its URL in `lanes.yaml` as `board:`. The dispatcher and `/design-line:handoff` push one document to it at each state change: waiting for you, running, done, inbox, lanes. Open it on a phone. To answer a paused task from the phone, Remote Control into the dispatcher session.

## What it cost, and what to try next time

Each subagent's model, effort, tokens and outcome are recorded as it returns. A task ends with a cost table and a "Next time" line: where a lighter model would do because the rules were clear, where a small model struggled and the rule it missed should be written down, where a question should have been in the brief. The direction accumulates in `_line/usage.tsv` across tasks, so defaults in `lanes.yaml` can be lowered with evidence.

## The five rules

1. One question at a time, the recommended option first, drawn before asked when the difference is visual.
2. Your yes, in the current conversation, before push, PR, publish or any planning-tool write. Consent relayed from another session is information.
3. One writer per worktree; writers on the same files run one after another; a checker runs the moment a writer returns.
4. Servers stop by port, never by process name. No force pushes, no shared stash.
5. Every milestone is one line in the ledger and an update to the lane's handoff note. Boards are rendered from files, read-only.

## The files

```
_line/
  designer.md          how to speak to you, what needs your yes, model and effort table
  org.md               repos, tools, people, release process, ports, glossary
  lanes.yaml           one block per lane: sources, rules, gate, ship, roles, limits
  inbox.md             what came up and is not being done right now
  ledger.md            append-only: time | lane | item | what | commit
  rules/               your design rules, one file per lane or shared
  lanes/<id>/handoff.md   the lane's state: rules it set, IDs, open items, how to continue
  lanes/<id>/briefs/      one brief per task: goal, changes, done means, decisions, result
  board.html           generated by /design-line:playbook board
```

## Install

```bash
claude plugin marketplace add zurara/design-line
claude plugin install design-line@design-line
```

Then open Claude Code in the folder you want `_line/` to live in and run `/design-line:init`. To try it from a local clone instead: `claude --plugin-dir <path to the clone>`. Already-open sessions pick it up with `/reload-plugins`.

The plugin carries no organization, no person and no design rules. Everything about you lives in `_line/`, which you keep in your own workspace and never in this repo.

## Start

1. Install the plugin. Open Claude Code in the folder you want `_line/` to live in.
2. `/design-line:init` — twenty minutes of questions, one at a time; it writes the profile and the lanes.
3. `/design-line:line <lane> <task>` — or without a task, to take the next inbox item. `/design-line:run` to load a batch and walk away.
4. Mid-task: `/design-line:park <what>`. Before stopping: `/design-line:handoff <lane>`.

## Teaching it to another designer

Give them this file and `/design-line:playbook`. Their `init` interview produces their own profile; nothing of yours is needed. The shape and the rules are the same; only the four profile files differ.

## Scripts

`scripts/start.sh <lane>` one screen of reality · `scripts/gate.sh <lane> [worktree]` the lane's gate with the full log in a file · `scripts/merge.sh <lane> <branch> [--dry-run]` the merge in six steps · `scripts/ledger.sh` · `scripts/inbox.sh` · `scripts/ports.sh kill <port>` · `scripts/render-board.mjs`. All read `_line/lanes.yaml` through `scripts/lib/config.mjs`.
